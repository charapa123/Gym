# dbt Design and Data Quality

## Why dbt?

The dbt part of the project was created to practise analytics engineering concepts using the same Google Forms source data.

It demonstrates:

- Layered modelling
- Raw-to-staging-to-presentation transformations
- Source definitions
- Generic tests
- Source freshness monitoring
- Documentation and lineage generation

---

## Project structure

The dbt project lives in `gym_tracker_dbt/`.

## Source layer

The source tables are defined in `_schema.yml` under the source name `raw`.

### `raw_form_answers`

Stores raw Google Forms response JSON and an insert timestamp.

This table contains historical response data.

### `raw_form_questions`

Stores raw Google Forms question metadata and an insert timestamp.

This table contains historical metadata loads, but only the latest metadata is used for transformations.

---

## Staging layer

### `Answers_model.sql`

Flattens the raw answer JSON into one row per response/question pair.

Important fields include:

- `insert_timestamp`
- `response_id`
- `create_time`
- `respondent_email`
- `question_id`
- `answer`

The model uses `jsonb_each` to expand the nested answers object:

```sql
jsonb_each(answers->'answers') AS q
```

### `Questions_filter.sql`

Filters question metadata to the latest inserted form structure.

```sql
ROW_NUMBER() OVER (ORDER BY insert_timestamp DESC) AS rn
```

Only `rn = 1` is retained.

### `Questions_model.sql`

Flattens the latest question metadata into a relational format.

It standardises exercise-selection questions using:

```sql
CASE
    WHEN item.value->>'title' LIKE '%Exercises%'
    THEN 'Exercises'
    ELSE item.value->>'title'
END AS title
```

It also extracts choice options from the Google Forms metadata. This supports dynamic exercise discovery without hardcoded exercise lists.

---

## Presentation layer

### `GYM_UPDATE.sql`

`GYM_UPDATE` is the final presentation model.

It joins answers to question metadata and pivots the response values into a set-level table:

```sql
MAX(A.answer) FILTER (WHERE Q.title = 'Which body part did you work out?') AS "Body_Part",
MAX(A.answer) FILTER (WHERE Q.title = 'How heavy was the weight?') AS "Weight",
MAX(A.answer) FILTER (WHERE Q.title = 'How many reps?') AS "Reps",
MAX(A.answer) FILTER (WHERE Q.title = 'Exercises') AS "Exercises"
```

The model is configured as incremental:

```sql
{{ config(
    materialized='incremental',
    unique_key='response_Id'
) }}
```

---

## Analytical grain

The final analytical grain is `response_id`.

Each row represents one completed exercise set:

```text
1 Google Form response = 1 exercise set
```

The final table contains:

- Response metadata
- Body part
- Exercise
- Weight
- Reps

This intentionally denormalised design is appropriate for downstream reporting and future Tableau development.

## Tests

The project includes dbt generic tests in `generic tests.yml`.

Examples include:

| Model | Column | Tests |
|---|---|---|
| `Answers_model` | `response_id` | `not_null` |
| `Questions_model` | `itemid` | `not_null` |
| `GYM_UPDATE` | `response_id` | `unique`, `not_null` |

Source-level tests are also configured for `raw_form_answers` in `_schema.yml`.

---

## Source freshness

Freshness monitoring is configured for `raw_form_answers`:

```yaml
freshness:
  warn_after:
    count: 12
    period: day
  error_after:
    count: 100
    period: day
loaded_at_field: insert_timestamp
```

This allows dbt to detect when upstream data has not been loaded within expected thresholds.

---

## dbt execution

The analytics workflow runs:

```text
dbt debug
dbt build
```

`dbt build` executes models and tests together, so transformation and validation happen in the same workflow.
